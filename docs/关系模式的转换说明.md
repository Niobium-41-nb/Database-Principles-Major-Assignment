## 2. 关系模式的转换说明

### 2.1 1:1 联系转换
- **无显式1:1关系**：系统中没有明显的1:1实体关系，所有主要实体都通过外键建立1:n或m:n关系

### 2.2 1:n 联系转换
1. **Users → CONTEST** (1:n)
   - 一个用户可以创建多个比赛
   - 转换方式：在CONTEST表中添加created_by外键引用Users.user_id

2. **CONTEST → PROBLEM** (1:n)
   - 一个比赛包含多个题目
   - 转换方式：在PROBLEM表中添加contest_id外键引用CONTEST.contest_id

3. **PROBLEM → TEST_CASE** (1:n)
   - 一个题目有多个测试用例
   - 转换方式：在TEST_CASE表中添加problem_id外键引用PROBLEM.problem_id

4. **Users → SUBMISSION** (1:n)
   - 一个用户有多个提交记录
   - 转换方式：在SUBMISSION表中添加user_id外键引用Users.user_id

5. **PROBLEM → SUBMISSION** (1:n)
   - 一个题目被多次提交
   - 转换方式：在SUBMISSION表中添加problem_id外键引用PROBLEM.problem_id

6. **CONTEST → SUBMISSION** (1:n)
   - 一个比赛包含多个提交
   - 转换方式：在SUBMISSION表中添加contest_id外键引用CONTEST.contest_id

### 2.3 m:n 联系转换
1. **PROBLEM ↔ PROBLEM_TAG** (m:n)
   - 一个题目可以有多个标签，一个标签可以标记多个题目
   - 转换方式：创建中间表PROBLEM_TAG_RELATION，包含复合主键(problem_id, tag_id)

2. **CONTEST ↔ Users** (m:n)
   - 一个比赛有多个用户参加，一个用户可以参加多个比赛
   - 转换方式：创建中间表CONTEST_USER，包含复合主键(contest_id, user_id)和额外属性

3. **Users ↔ SUBMISSION (Hack)** (m:n)
   - 一个用户可以Hack多个提交，一个提交可以被多个用户Hack
   - 转换方式：创建HACK表，包含hacker_id和submission_id外键
